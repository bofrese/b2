# b2 Knowledge — Command and Skill Reference

*Update this file whenever any skill, command, or resource inside `b2/` changes. Single source of truth for what b2 does and how it fits together.*

---

## Flow Overview

```
/b2:talk (anytime — explore ideas, capture notes, feeds all steps below)
/b2:vision → /b2:brand → /b2:structure → /b2:write → /b2:design → /b2:sync → /b2:setup
```

After setup, day-to-day: `/b2:write` → `/b2:build` → `/b2:serve` → `/b2:website-review`

SEO: `/b2:seo` — run anytime after first build. Audits dist/, fixes src/partials/theme/, generates sitemap + robots.txt. Re-run after major content changes.

For illustrations: `/b2:illustrate` (first run: style brief interview → saves `docs/product/illustration-style.md`; subsequent runs: generates prompts → optional API generation or external tool → evaluates result → iterates until approved)

For presentations: `/b2:present` — anytime, any topic. Mode-detects create (context harvest → strategic interview → outline approval → reveal.js-flavored markdown) vs. edit (surgical content changes, no re-interview). Outputs to `docs/presentations/{slug}/{slug}.md`. Dispatches to `/b2:present-design` (theme interview + mockups + lock, once per theme — reuses the website's design language) and `/b2:present-build` (renders/reconciles the deck's HTML at `website/dist/presentations/{slug}/`, applying the resolved theme; standalone, per-deck, never automatic).

Run `/b2` at any time to see current status and what to do next.

## Key Design Decisions

**THEME variable:** Set by the user during `/b2:design` Phase E (theme name question). Written to `website/b2.cfg` as `THEME=`. All other skills read from there (default: `b2`). No skill hardcodes `website/theme/b2/`. To switch themes, update `THEME=` in `b2.cfg` and re-run `/b2:setup`.

**BASE_PATH:** Generated with `/` paths by design-expert. Setup-expert patches `header.html`/`footer.html` with sed when `BASE_PATH≠/`. Re-running setup reapplies.

**mockup.html in theme:** The chosen concept is copied to `website/theme/{THEME}/mockup.html` with inline CSS/JS stripped. The originals in `website/mockups/` stay self-contained. `mockup.html` requires the local server to render.

**Bob compatibility:** `/b2:brand` writes `website-design-brief.md`. Most skills fall back to `design-brief.md` if `website-design-brief.md` is missing. **Exception — `/b2:design`:** it does not treat `design-brief.md` as an alias. If `website-design-brief.md` is missing, it offers to create it (a thin wrapper over the product `design-brief.md` when one exists), because the two are distinct scopes — product/app brief vs the brief for the website about it. See `docs/domain/bob-b2-coexistence.md`.

**Creative freedom / any-library support (full lifecycle):** Mockups (Phase C) may use any CDN library, web font, external CSS, animation/3D/WebGL, and linked assets — no dependency whitelist. Phase E carries the chosen mockup's **entire** front-end into the theme: full CSS → `styles.css`, full JS → `scripts.js`, all CDN library/font links → `header.html`/`footer.html`, self-hosted libs as extra theme `*.js`/`*.css`, and binary assets (fonts, models, video) under `theme/{THEME}/assets/`. The build copies all theme `*.css`/`*.js` and `theme/{THEME}/assets/` to `dist/`, so any library/font/style works on the live site. Per-page bespoke interactive/3D elements are supported by registering them as components (CSS in `styles.css`, JS in `scripts.js`) or, for one-offs, a scoped `<style>`/`<script>` in the partial — `/b2:sync` preserves both. The semantic-class component contract remains the default for standard content (keeps theme-swappability).

**Redesign — semantic-class reuse (soft):** When `/b2:design` runs on a site that already has a theme, the mockup agents and `components.md` get the existing class vocabulary as a **soft reuse hint** — reuse names where the new design has an equivalent element (`.hero`, `.site-nav`, `.post-card`), so existing partials survive a theme swap. It is a suggestion, never a constraint: a bold redesign adds/renames classes freely. `components.md` records a `## Redesign delta` (Reused / New / Dropped-renamed); `/b2:sync` Step 1b re-evaluates partials against it — reused → kept, renamed → remapped, dropped/changed → redone. Reuse makes swaps cheap without capping creativity.

**Generic design foundation (`b2/shared/design/`):** the generic design concern (named things + judgment, incl. the moved `web-design-principles.md`) shared across b2's design skills via `${CLAUDE_PLUGIN_ROOT}/shared/design/`. Loaded per-phase (progressive disclosure), not as an invoked skill. b2-internal — bob designs UI independently via `bob:ui-design`; the plugins integrate only through project files, one-way (bob wraps b2), never by reading each other's internals.

**Build offers:** Write, sync, and design all offer to run build after completing their primary work. The user can say yes to chain into build-expert automatically.

**API key storage:** `GEMINI_API_KEY` and `GOOGLE_PAGESPEED_API_KEY`/`PAGESPEED_API_KEY` are stored in `.env` at the project root (not in `b2.cfg`) — same convention for both. `.env` should be in `.gitignore`. `b2.cfg` contains only build config (`THEME`, `BUILD_TOOL`, `BASE_PATH`, `SITE_URL`) and is safe to commit. PageSpeed works without a key on a small shared quota that's often already exhausted (a global bucket, not per-IP) — a free key removes this; see `seo-expert/references/pagespeed-api-key.md`.

**SEO variable injection happens at build time, not as a post-hoc SEO patch:** `build-expert`'s `assemble.sh` (and, for projects with a hand-rolled Makefile, the project's own vendored assembler script) injects `{{TITLE}}`/`{{DESCRIPTION}}`/`{{CANONICAL}}`/`{{OG_*}}` into `header.html` from `src/*.md` frontmatter + `b2.cfg`'s `SITE_URL` on every build. This used to be something `/b2:seo` fixed after the fact (duplicate titles/descriptions across every page until someone noticed); now every b2 site gets distinct per-page SEO metadata from the first build. `/b2:seo` still owns verifying it (unfilled `{{ }}` placeholders, broken og:image files) and filling in content that needs judgment (schema, alt text, actual title/description copy).

**Cache-busting is build-time, same mechanism as SEO injection:** `{{ASSET_VERSION}}` (a content-hash of `styles.css`+`scripts.js`, computed fresh by every assembler — `build-expert/scripts/assemble.sh`, `seo-expert/references/assemble-template.sh`, and any hand-rolled project Makefile that mirrors the pattern) gets appended as `?v=` on their `<link>`/`<script>` tags. It exists because a static filename never changes across deploys, so a browser with no explicit cache header (mobile Safari especially) can keep serving last month's CSS after a redesign with no way to know it's stale. `/b2:setup` pairs this with `website/src/.htaccess`: no-cache on HTML (always revalidate), 1-year immutable on CSS/JS (safe now that the URL itself changes when content does).

**Sequence, don't cut — the site-speed principle:** a slow paint is a scheduling problem, not a "too much animation" problem. Never propose removing an effect, background, or decorative element to improve a speed score; reorder it instead — anything not needed for first paint waits behind `requestIdleCallback`/`window.load`. Applies across `design-expert` (how effects get built) and `seo-expert` (how PageSpeed findings get diagnosed and fixed).

**Background removal:** After illustration approval, `/b2:illustrate` offers to strip the background using `rembg` (`pip install rembg`). Outputs a transparent PNG alongside the original. Only suggested for use cases that need it (spot illustrations, icons) — not for heroes or full-bleed headers.

**Illustration flow:** `/b2:illustrate` generates prompts — it does not directly produce image files. The user generates images externally (or via optional Gemini API if a paid key is present) and provides the result for evaluation. The skill evaluates, iterates, and at session end proposes style brief updates if the approved image diverged from `docs/product/illustration-style.md`.

**Presentation theme vs. deck are decoupled (many decks, one theme):** `/b2:present-design` runs once per theme, never once per presentation — same relationship as `/b2:design`'s one website theme serving every page. A deck's `theme:` frontmatter is the only link between the two; `/b2:present-build` resolves it automatically when only one theme exists.

**No bespoke diff/patch engine for presentation surgical update:** `present-build-expert` reconciles a deck's slides by id using the exact pattern `sync-expert` already established for pages — a git diff of the source (committed-since-last-build + uncommitted, falling back to mtime), read and interpreted by the AI, never a scripted patch algorithm. This codebase has never built one; presentations don't either. When no git repo exists (or the output `.html` has uncommitted edits), the same per-slide-by-id parsing is reused for a semantic `.md`-vs-rendered-`.html` compare instead of a diff hunk — `.md` always wins on divergence, and dropping a removed slide asks first (unlike the git path's safe silent drop, this path has no history to recover from).

**Presentation render is sequential and deck-wide, not parallel-per-slide:** unlike `design-expert`'s parallel mockup agents (which want 2-3 *divergent* concepts), `present-build-expert` authors a deck's changed/new slides in one continuous pass so the whole deck reads as one coherent hand-crafted piece. Reach for parallel-agent-per-unit only when units should diverge in isolation; sequential single-context generation when units must cohere.

**Presentation output is assembled incrementally, not written once at the end:** `present-build-expert` writes the reveal.js shell once (empty slide container) before authoring begins, then appends each slide's `<section>` to the live output file as it's generated or copied forward — never a single end-of-pass full-file write. This is what makes the default per-slide visual-propose loop possible: the user can refresh the live deck URL and see each accepted slide immediately, mid-build, because the file already reflects it. A workflow with both a human-in-the-loop step and a final-assembly step should generally build incrementally if the human needs to see intermediate state — a single terminal write forces the loop to either not exist or write to something other than the real output.

**Verification cost should scale with what changed and whether a human already reviewed it, not with deck/page size:** `present-build-expert`'s verification gate is 3 tiers — two cheap, deck-size-independent checks that always run (one scripted sweep through every slide for console errors, one Overview-mode screenshot), and one expensive per-slide check (full screenshot + computed-style/animation sampling) reserved for slides classified new/changed with a real visual change, and skipped entirely when the user already reviewed that slide live via the interactive propose/accept loop. Before adding an automated check to a workflow that also has human review, gate the automated check to only the paths that bypass human review.
